## Findings considered and rejected

- **Detect skill content drift via `computedHash` in `skills-lock.json`.**
  Rejected — not blocked, redundant. The `skills` CLI that writes the lockfile
  ships `skills update`, which owns exactly this. Reimplementing it would
  duplicate a tool the user already has, and the hash is not reproducible from
  `SKILL.md` bytes anyway (0/26 match `sha256(SKILL.md)` on a pristine install).
  If drift reporting is ever wanted here, shell out to `skills` rather than
  reverse-engineering the digest.

- **Check that an agent's frontmatter `name` matches its filename.** Rejected —
  16 of 34 agent files in the fleet differ, and every one inspected was
  intentional (`engineering-api-platform-engineer.md` declares
  `name: API Platform Engineer`). Unlike skills, nothing keys on the agent
  filename. This would be a 16-false-positive check. Recorded so it is not
  re-proposed; plan 003 carries a regression test against it.

- **Expand or restore `DEP_SKILL_MAP` (dependency → skill suggestions).**
  Rejected and already deleted in `e1c9976`. The 7-entry version fired on 0 of
  17 projects, and making it useful means owning a registry that tracks an
  ecosystem. Skill provenance comes from `skills-lock.json` instead.

- **Report `.claude/settings.local.json` files tracked by git** (4 real hits:
  dialyx, dream-detailing-project, nicmarmir, touchagency). Deferred, not
  rejected — the finding is real, but the check needs to know what git tracks,
  and agentscan is currently pure-filesystem with no subprocess calls. That is a
  dependency decision for the maintainer, not something an executor should
  decide inside a plan.

## Open architectural question (not a plan)

All 37 actionable findings come from `src/checks/` (code). The YAML rule engine
(`src/rules/engine.ts`, ~590 lines, the largest file in the repo) produces only
`info`-severity budget rules plus one package-manager drift rule. Its DSL also
fails silently on a typo'd clause — documented, but a trap for the user-authored
rules that are its only justification.

Deciding whether to invest in the engine (fix silent failure, add the `any` /
`hasMcp` / `hasHook` matchers the original spec promised) or shrink it is a
maintainer call, not executor work. It is recorded here so it is not lost.
